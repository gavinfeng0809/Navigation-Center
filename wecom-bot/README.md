# 企微「重要通知」自动归档采集器

把企微群里发的**重要通知**，一键归档进 [重要通知中心](http://10.127.207.71:8091)。

用法就一句话：**群里发重要通知时，@一下这个机器人。**

---

## 一、为什么是「@即归档」，而不是全自动

企微侧能拿到消息的通道只有三条，官方文档的定性如下：

| 通道 | 能否拿到群消息 | 依据 |
|---|---|---|
| 群机器人 webhook | ❌ 只能发不能收 | 官方目录里它归在「消息推送（原"群机器人"）」下，只有推送方向 |
| 智能机器人 | ⚠️ **只在被 @ 时**收到那一条 | [接收消息](https://developer.work.weixin.qq.com/document/path/100719) 列的触发场景全是「用户**群里@智能机器人**或者单聊中发送…」 |
| 会话内容存档 | ✅ 全部消息 | [获取会话内容](https://developer.work.weixin.qq.com/document/path/91774) 返回 `msgid`/`roomid`/`msgtype`/`content` |

**所以想要真正全自动（不用人 @），只有「会话内容存档」一条路**，而它要满足：
企业认证 → 管理后台开通 → 上传**企业确认函**（审核约 3 个工作日）→ 同意服务协议 → 购买授权 → 成员同意存档。
这套流程走完通常以周计，而且本地存档那份是**收费**的
（[数据与智能专区](https://open.work.weixin.qq.com/help2/pc/21537) 那份专区存档免费，但数据不落地本地、只能拿脱敏结果，喂不进 notice-hub）。

本采集器走的是**当下就能上线的折中方案**：把「@机器人」这个动作当成归档开关。
零成本、不用认证、不用确认函、不买授权、不改任何现有流程，代价是发的人要多 @ 一下。

> 如果哪天会话内容存档开通了，本采集器不用改结构：
> 把 `ext_id` 继续用企微的 `msgid`，换成从存档接口拉消息即可（notice-hub 按 `ext_id` 幂等，重复投递不会脏数据）。

## 一·四、入库时自动整理重点（规则版，不调模型）

企微内容入库前会自动跑一遍整理，产出：

```
【重要通知】客户公网IP回收注意事项

关键字：客户 / 供应商 / 变更 / 邮件 / 工单

【要点】
1. 客户：星海科技（XHKE）
2. 涉及IP：203.0.113.10 / 203.0.113.11

【正文】
各位同事：

**接供应商通知，以下客户公网IP需要回收，请相关同事在 2026-10-20 前完成确认。**
```

关键字会**同时**写进正文的「关键字：」行和 `tags` 字段（页面左侧筛选/搜索直接可用）。
`AUTO_POLISH=0` 可关掉。

**这套规则不是新写的**，是把页面上「一键整理重点」那段 JS
（`public/notices.html` 的 `polishRecord` / `polishKeywords` / `POLISH_LEXICON`）
逐行移植成 `polish_rules.py`。移植而不是重写，是因为那套规则调过参数
（词表权重、关键字去重、行分类、标题挑拣），重写必然对不上——
页面点出来的和企微自动整理出来的会长得不一样。

**一致性由测试盯着**：

```bash
node wecom-bot/test_polish_parity.js
```

它把页面里**真实的 JS 源码**抽出来在 Node 里跑，再把同一批输入喂给 Python 版，
两边输出必须**逐字节相同**。以后改了任一边，这个测试立刻报错。
（改 `polish_rules.py` 请同步改 `notices.html`，或反过来——别只改一边。）

能做到：认头部字段 / 摘出要点行并编号 / 行动句加粗 / 顶部补「关键字」。
**做不到：真正的语义归纳**（比如「【一句话】」摘要），那需要模型 —— 见下一节。

## 一·五、语义摘要：交给 Hermes，和邮件走同一条路

企微进来的正文**默认只做原样归档**，不做摘要——notice-hub 服务端没有任何模型调用能力
（这是刻意的，见 `inbox/README-页面粘贴模板.txt`）。真正的「关键字 / 一句话 / 要点」
由 **Hermes** 补。

交接方式就是一个标签：

```env
TAGS=待汇总
```

`待汇总` 是 Hermes 的**认领凭据**。它扫到这个标签，就把正文重构成：

```
关键字：YSGJ央视国际 / SLA监控 / IPVPN / 可用性告警 / 延迟 / 丢包 / vipcustomeralert

【一句话】钻石客户央视国际（YSGJ）IPVPN 已开通全程 SLA 监控，告警发 vipcustomeralert@…，
收到告警按下面三步处置。

【处置流程】
1. …
【备注】…
```

并把标签换成真正的关键字，同时补上分类与级别。

**这个标签必须和邮件链路一致**——`tools/inbox_pipeline.py` 的 `--tags` 默认值就是 `待汇总`。
两边用同一个标签，Hermes 才会用同一套流程处理，页面上看起来才一样。
只想要原样归档、不做分析，把 `TAGS` 改回 `企微自动归档` 即可。

> 已入库但还没分析的条目不会被自动补标签。要回填就改一下 `notices.tags`。

## 二、为什么用「长连接」而不是「回调地址」

企业微信官方对两种模式的对比（[长连接文档](https://developer.work.weixin.qq.com/document/path/101463)）：

| 特性 | Webhook（短连接） | **WebSocket（长连接）** |
|---|---|---|
| 服务端要求 | **需要公网可访问的 URL** | **无需固定的公网 IP** |
| 加解密 | 需要对消息加解密 | **无需加解密** |
| 延迟 | 较高（每次建连） | 低（复用连接） |
| 可靠性 | 高（无状态） | 需心跳保活、断线重连 |

notice-hub 只监听内网网卡 `10.127.207.71:8091`（[docker-compose.yml](/data/notice-hub/docker-compose.yml) 里刻意这么配的），
企微服务器根本回调不到它——所以**长连接是唯一可行的选择**，而且顺带省掉了整套加解密。

链路是**本机主动外连** `wss://openws.work.weixin.qq.com`，不需要在防火墙上开任何入向端口。

## 三、需要企微管理员做什么（可整段转发）

> 请帮我建一个「智能机器人」并开启长连接 API 模式：
>
> 1. 企业微信管理后台 → **智能机器人** → 新建一个机器人
>    名称建议「通知归档助手」，可见范围请包含**运维值班群**所在的部门/成员
> 2. 在机器人配置页开启 **API 模式**，方式选 **长连接**
>    （不要选「设置接收消息回调地址」——我们的服务器在内网，企微回调不到）
> 3. 把生成的两个值发我：**BotID** 和 **Secret**
>    （Secret 是长连接专用密钥，与回调模式的 Token/EncodingAESKey 不是一回事）
> 4. 把这个机器人**拉进运维值班群**（以及其它要归档通知的群）
>
> 说明：这个机器人只做「归档」——群里 @它一下，它把那条消息存进我们的重要通知中心，
> 并在群里回一条「已归档」。它**收不到**群里没 @ 它的消息，也不会读取其它任何会话内容。
> 不需要企业认证、不需要付费、不改变任何现有流程。

拿到 BotID 和 Secret 之后，本采集器即可上线。

## 四、上线步骤

```bash
cd /data/notice-hub/wecom-bot

# 1. 填凭证（其余项一般不用改）
vi config.env          # WECOM_BOT_ID=... / WECOM_BOT_SECRET=...

# 2. 自检：查配置、notice-hub 连通性、令牌有效性、目录可写
./venv/bin/python wecom_bot.py --check

# 2b. 真连一次企微，确认 BotID/Secret 有效（强烈建议做）
#     凭证错的表现是「服务正常起着、群里 @ 了却没反应」，要翻日志才能定位；
#     这一步把它变成一条带退出码的结论。
./venv/bin/python wecom_bot.py --verify

# 3. 装服务并启动
cp wecom-bot.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now wecom-bot

# 4. 看日志确认认证成功
tail -f /data/notice-hub/data/wecom-bot.log
#   看到「🔐 长连接认证成功，开始接收 @ 消息」就成了

# 5. 去群里 @一下机器人发条测试消息，然后刷新重要通知中心
```

### 发布人显示名（可选，建议做）

企微的消息回调里 `from` **只有 `userid`**（形如 `FengXuJie`），**没有显示名**；
长连接 SDK 也没有查用户资料的接口（`WeComApiClient` 只有文件下载）。
所以「页面上显示 Gavin Feng 而不是 FengXuJie」这件事，只能靠一份映射表：

```env
USER_NAMES=FengXuJie=Gavin Feng,HanZheng=韩征
```

没配到的会原样显示 userid，并在日志里打一行提示（每个 userid 只提示一次），
照着补就行。原始 userid 会另存到 `sender` 字段，详情页显示成
`CSE-小组长群　<FengXuJie>` —— 同名同姓或有人改了显示名时，靠它才能对得上人。

> 想全自动拿姓名，得另建一个**自建应用**、给它通讯录读取权限，
> 用 corpid + 应用 secret 调 `user/get`。当前只有机器人的 BotID/Secret，做不到。

### 群名映射（可选，建议做）

第一次收到消息时，日志会打出那条消息的 `chatid`。把它填进 `config.env`，
页面上「来源」列就会显示中文群名而不是一串 chatid：

```env
CHAT_NAMES=wrOgQhDgAAxxxx=运维值班群,wrOgQhDgBByyyy=网络变更群
```

## 五、运维

| 事项 | 命令 |
|---|---|
| 看日志 | `tail -f /data/notice-hub/data/wecom-bot.log` |
| 重启 | `systemctl restart wecom-bot` |
| 自检（不连企微） | `cd /data/notice-hub/wecom-bot && ./venv/bin/python wecom_bot.py --check` |
| 验证凭证（真连企微） | `./venv/bin/python wecom_bot.py --verify` |
| 不写库试跑 | `./venv/bin/python wecom_bot.py --dry-run` |
| 整理规则一致性对拍 | `node test_polish_parity.js`（Python 版 vs 页面 JS，必须逐字节一致） |
| 本机联调（不连企微） | `./venv/bin/python test_e2e.py` |
| 重建虚拟环境 | `python3 -m venv venv && ./venv/bin/pip install -r requirements.txt` |

**注意事项**

- **同一机器人只能有一条长连接**：官方限制「新连接会踢掉旧连接」。
  所以**不要**在两台机器上同时跑同一个 BotID 的采集器；要主备就别同时连。
- 服务配了 `Restart=always` + SDK 无限重连（`max_reconnect_attempts=-1`），
  企微侧抖动会自己恢复，不用人工干预。
- 入库失败的消息会落到 `state/pending.jsonl`，下次收到消息或重启时自动重投。
  notice-hub 按 `ext_id`（=企微 `msgid`）幂等，**重复投递只会更新、不会产生重复通知**。
- **被动回复有 5 秒窗口**：所以交互路径只试一次入库（`attempts=1`），失败立刻落
  pending 并在后台重投。如果在这里加退避重试，退避时间会吃掉窗口，回执就永远发不出去。
- **同一机器人只有一条长连接的另一个后果**：跑 `--verify` 会把正在运行的服务踢下线
  （它自己会重连回来）。要验证就趁服务停着，或者接受它重连一次。

## 七、常见问题

**Q：机器人收不到消息？**
A：按顺序查——① 机器人是否已被拉进那个群；② 是否有 @ 它（不 @ 收不到，这是企微的限制）；
③ `ALLOW_CHATTYPES` / `ALLOW_CHATIDS` 是否把它挡了（日志会打「⏭ 跳过」）；
④ 日志里有没有「长连接认证成功」。

**Q：日志报 `WECOM_BOT_ID 未配置`？**
A：还没填凭证，服务会主动退出（exit 2）而不是空转。

**Q：标题取得不对？**
A：标题默认取正文首个非空行；如果首行只是 `【重要通知】` 这种标记行，会自动跳到下一行。
想彻底自定义，改 `wecom_bot.py` 里的 `derive_title()`。

**Q：图片没存下来？**
A：图文混排里的图片会下载到 `public/wecom-media/` 并在详情页显示；
下载失败**不影响正文归档**，日志里会记一条 ⚠️。单聊的图片/文件/视频消息企微只推 URL+解密密钥，
本采集器目前只处理图文混排（`mixed`）里的图片。

**Q：想改成「不 @ 也归档」？**
A：做不到——企微不推。要么升级到会话内容存档，要么保持现状。

**Q：关键字标签是自动的吗？【一句话】摘要呢？**
A：分开的两件事——
· **关键字**：**自动**。入库时跑规则版整理（`AUTO_POLISH=1`），当场就有，
  和页面「一键整理重点」是同一套规则。
· **【一句话】语义摘要**：**不自动**。规则做不到语义归纳，得靠模型。
  条目带着 `待汇总` 标签（和邮件链路同一个标签），由 Hermes 按需补。
  注意 Hermes 那一步本来就不是定时的，邮件一直是「人工/模型按需补」。

**Q：发布人显示的是 FengXuJie，不是企微里的名字？**
A：回调里只有 userid，没有显示名，得在 `USER_NAMES` 里配映射（见上文）。
没配到的会原样显示 userid 并在日志里提示。已经入库的历史条目不会被自动改，
需要回填的话改一下 `notices.publisher` 即可。

**Q：语音 @机器人 能归档吗？**
A：能。企微**在服务端就把语音识别成文字**了，推下来的是 `voice.content` 里的转写文本，
没有音频、没有 aeskey，直接当正文用。所以语音和打字走的是同一条路。

**Q：日志显示「已入库」但群里没看到回执？**
A：八成是回执的 `msgtype` 用错了。**被动回复（`aibot_respond_msg`）不接受
`markdown`** —— 它只认 `stream` / `text` / `template_card` / 媒体；
`markdown` 是**主动发送（`aibot_send_msg`）专用**的。
用错时企微会静默拒收那一帧：库里有、群里没有。
本采集器统一走 `stream`（`finish=True`），`mock_ws_server.py` 也复刻了这条校验，
所以以后再犯会在联调阶段直接失败，不会拖到线上。

**Q：同事把机器人当搜索用了，发「帮我查询一下最近的通知」会怎样？**
A：**不会被归档**（`SKIP_QUERIES=1`，默认开），只会回一条说明，告诉他去通知中心查。
这不是假想 —— 上线第一天就真发生了：那条「帮我查询以下近期的重要通知内容」
被当成「重要通知 / urgent」归档，成了通知中心里的一条垃圾。

识别规则刻意做得很窄：只看**开头**（敬语后紧跟查询类动词，或「有没有/哪些/什么」这类
疑问词打头），并且限定 50 字以内。这是有意的取舍 —— 漏判只是少归档一条、而且发的人
会收到回执（可补救），误判则是**静默丢掉一条真通知**。
想退回「只要 @ 就归档」，把 `SKIP_QUERIES` 设成 0。

**Q：改了处理逻辑，怎么确认没把回执弄坏？**
A：`./venv/bin/python test_e2e.py`。mock 会校验回执类型、封口帧是否为空、
`stream.content` 是否超 20480 字节，并把问题打成 `✗`。
