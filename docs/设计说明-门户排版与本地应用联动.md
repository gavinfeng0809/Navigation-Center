# notice-hub 设计说明：门户排版改造 + 本地应用联动

> 版本：v1（待评审）
> 范围：两件事 —— ① 门户「找东西慢」的排版改造；② 点链接用本地应用打开 + 账号密码自动填。
> 本文只做设计说明，**未改动任何代码**。

---

## 0. 结论摘要（先看这段）

| # | 事项 | 结论 | 前置依赖 |
|---|---|---|---|
| 1 | 门户排版 | **可做，收益最大、风险最低**，建议先做 | 无 |
| 2 | Winbox 本地打开 | **可做**，需要 Windows 侧装一个小启动器 | 无（但与 3 共同设计更好） |
| 3 | Web 页面账号密码自动填 | **可做，但有硬性前置条件** | ⚠️ 必须先有 TLS，否则密码在内网明文传输 |
| 4 | 浏览器自带密码管理器 | **已经能满足 90% 的 web 自动填需求，零开发零风险** | 无 |
| 5 | 集中式凭据库 | 会让 notice-hub 从「导航页」变成「265 台防火墙的密码库」，单点风险高 | TLS + 登录限流 + 审计 |
| 6 | 顺路发现 2 个 bug | 265 台 FortiGate 的在线状态点**永远是灰的**（`is_private_host` 漏判 + 串行探测） | 无，1 行 + 1 处改造 |

**我的建议**：先做 1（排版），再决定 2/3 走哪条路。第 4 项我强烈建议你先试一下再决定要不要做 5 —— 详见 §4.1。

## 1. 现状与问题

### 1.1 排版问题的根因

门户页面 `#/portal` 目前的行为是**一次性把 272 张卡片全部展开渲染**：

| 事实 | 数值 |
|---|---|
| 导航项总数 | 272 项 |
| 分组数 | 18 个 |
| 首屏渲染卡片数 | **272 张（全部分组默认展开）** |
| 最大分组 | 客户站点防火墙 **89** 项（下含 16 个客户子分组） |
| 第 2–5 大分组 | SASE POP 25 / 门户与云账号 23 / 系统与平台 22 / 网络工具与查询 19 |
| 卡片网格 | `grid-template-columns: repeat(auto-fill, minmax(198px,1fr))`，宽屏约 5–6 列 |
| 分组标题可点击？ | **否**（`.gh` 无折叠逻辑） |
| 二级分组可折叠？ | 是，但**默认展开**（`.navsub` 未被加上 `collapsed`） |

代码位置：`public/index.html` 的 `groupBodyHtml()` 与 `renderPortal()`。
`renderPortal()` 把 18 个 `<section class="navgroup">` 全部拼进 DOM，没有任何折叠状态。

### 1.2 两个「已经在库里、但没接到界面上」的能力

这是本次改造性价比最高的部分 —— **数据已经有了，只是没被使用**：

**① `favorite`（常用）字段完全闲置**

- 数据库有 `nav_items.favorite` 列
- 管理表单有「常用」勾选框（`#nfFav`）
- CSS 有「常用」徽章样式（`.me`）
- 门户渲染 `navCardHtml()` 里 **一次都没用到 `favorite`**
- 272 项中 `favorite=1` 的有 **0 项**
- 排序里的 `ORDER BY favorite DESC, sort, id` 因此完全空转

**② 访问频次在记录，但没用于排序**

- `visit_count` / `last_visit` 由 `POST /api/nav/visit` 写入
- 目前只有 **10 项**有访问记录
- 「最近访问」只显示 6 个 chip
- 组内排序不按频次

### 1.3 一个结构性问题：89 项的「客户站点防火墙」

该分组下 16 个客户子分组，当前是 16 个「小标题 + 网格」块**纵向堆叠且全部展开**。
即便做了分组折叠，展开这一个分组仍会一次性铺开 89 张卡片。

→ 需要针对「大分组 + 多子分组」单独设计（见 §2.2-B）。

## 2. 门户排版改造

### 2.1 目标

- **首屏能看完全部 18 个分组**（而不是滚过 272 张卡）
- **日常那十几个系统 1 次点击内到达**（不滚动、不进分组）
- **知道名字时 3 秒内到达**（键盘流）
- 保持现有视觉语言（暗色卡片风、`--accent`、圆角 11px），不做整体重绘

### 2.2 交互设计

#### A. 分组可折叠 + 默认全折叠 + 记住状态

- `.gh`（分组标题行）整行可点击，箭头指示展开态
- **默认全部折叠**，首屏 = 18 行目录，一屏内看完
- 展开状态存 `localStorage`，按分组 id 记忆（键：`nh.navOpen`）
- 分组标题右侧显示项数徽章（已有 `.gc` 样式可复用）
- 展开/折叠带 120ms 过渡，避免跳动

```
未展开时的一屏：
┌──────────────────────────────────────────────────────┐
│ 🔍 Ctrl+K 搜索系统名称 / 描述 / 标签 / IP              │
├──────────────────────────────────────────────────────┤
│ ★ 常用    [Zabbix] [Grafana] [KARL-001] [SZLR-001] …  │
├──────────────────────────────────────────────────────┤
│ ▸ 网络运维                                        1 项 │
│ ▸ 监控告警                                        3 项 │
│ ▸ 排班管理                                        1 项 │
│ ▸ 效率与安全                                      1 项 │
│ ▸ KARL 站点防火墙                                17 项 │
│ ▸ 客户站点防火墙                                 89 项 │
│ ▸ SASE POP                                       25 项 │
│ ▸ 集中管理平台                                   11 项 │
│ ▸ Forti 文档与工具                               14 项 │
│ ▸ 系统与平台                                     22 项 │
│ ▸ 流量与监控                                      8 项 │
│ ▸ POP 服务器                                     13 项 │
│ ▸ 机房与授权                                      5 项 │
│ ▸ 网络工具与查询                                 19 项 │
│ ▸ 门户与云账号                                   23 项 │

│ ▸ 其它工具                                       14 项 │
│ ▸ AI                                              1 项 │
└──────────────────────────────────────────────────────┘
```

#### B. 大分组：子分组改成「筛选 chip」，不做纵向堆叠

针对 89 项的「客户站点防火墙」（16 个客户）：

- 子分组名渲染成一行 **筛选 chip**：`全部(89) | ATKN(3) | HRCX(2) | JYZN(5) | …`
- 点某个 chip → 下方网格只显示该客户的项（默认选中「全部」？**建议默认选中"第一个客户"或"上次选的客户"**，避免一进来又是 89 张）
- chip 上带项数，一眼看出哪个客户设备多
- 选中状态存 `localStorage`（键：`nh.navSub.<groupId>`）

这样 89 项被拆成 ~6 项一屏，且切换客户是 1 次点击。

#### C. ★ 常用区（接通常用的 `favorite` 字段）

- 门户顶部固定「常用」区，最多显示 12 个（超出显示「…更多」）
- 卡片右上角加 **★ 星标按钮**，点击即切换 `favorite`（调已有的 `PUT /api/nav/items/<id>`）
- 未登录 / 非管理员时 ★ 只读（因为写接口需管理员）；可考虑加一个「我的常用」用户级字段（见 §2.4 决策点）
- 常用区为空时整块隐藏，不占地方

> ⚠️ 注意：`favorite` 目前是**全局**字段（所有用户共享）。如果只有你一个人用，全局即可；多人用则需要改成用户级。见 §6 待确认项。

#### D. Ctrl+K 命令面板（键盘直达）

- `Ctrl+K` 或 `/` 聚焦；`↑` `↓` 选择；`Enter` 打开；`Esc` 关闭
- 输入即时过滤（复用现有 `data-search` 索引，已是 `名称+描述+标签+URL` 全小写拼接）
- 结果列表**跨分组扁平展示**，每行显示：状态点、名称、分组/客户、host
- 排序：**常用优先 → 访问频次高优先 → 名称匹配位置**
- 回车 = 打开当前高亮项

```
┌─────────────────────────────────────────────┐
│ > karl-00█                                   │
├─────────────────────────────────────────────┤
│ ▸ KARL-003 004 BJ   客户站点防火墙/…  213:…  │ ← Enter 打开
│ ▸ KARL-001 201F SH  客户站点防火墙/…  161:…  │
│ ▸ KARL-005 81F GZ   客户站点防火墙/…  190:…  │
├─────────────────────────────────────────────┤
│ ↑↓ 选择 · Enter 打开 · Esc 关闭   3 个结果    │
└─────────────────────────────────────────────┘
```

#### E. 按访问频次排序

- 组内排序改为：`favorite DESC, visit_count DESC, last_visit DESC, sort, id`
- 常用/常去的项自动浮到前面，不需要手工调序
- 「最近访问」chip 从 6 个提到 10~12 个

#### F. 搜索结果扁平化

现在搜索是在展开的分组间就地过滤高亮，结果**散落在各分组里**仍要滚动。
改为：搜索时直接切换到 §2.2-D 的扁平结果列表（同一套渲染）。

### 2.3 视觉与无障碍

- 分组折叠行高 44px，hover 整行高亮（`--panel2`）
- 箭头图标旋转 90° 表示展开（复用现有 `ic('caret')` 与 `.subh svg` 的过渡写法）
- `aria-expanded` / `role="button"` / `tabindex=0`，支持 Enter/Space 展开
- 首屏卡片数量从 272 降到约 12（常用区），**首次渲染 DOM 节点减少约 95%** → 首屏也会更快

### 2.4 数据与接口影响

**前端为主，后端改动很小：**

| 改动 | 位置 | 说明 |
|---|---|---|
| 分组折叠状态 | 纯前端 | `localStorage`，无需后端 |
| 子分组 chip 筛选 | 纯前端 | 数据已在 `items[].subgroup` |
| Ctrl+K 面板 | 纯前端 | 复用 `data-search` |
| ★ 常用切换 | 复用已有接口 | `PUT /api/nav/items/<id>`（需管理员） |
| 组内按频次排序 | **后端 1 行** | `nav_list()` 的 `ORDER BY`，或前端排序 |
| 常用区数据 | 前端过滤 | `items.filter(i => i.favorite)`，无需新接口 |

**结论：§2 几乎不碰后端，不动数据库结构，是本方案里最安全的一块。**

### 2.5 分期

- **P0**：分组折叠（默认折）+ ★ 常用区 + Ctrl+K 面板 → 解决 95% 的「找半天」
- **P1**：大分组子分组 chip 筛选 + 频次排序 + 搜索结果扁平化

## 3. 打开方式（launch mode）：用本地应用打开

### 3.0 前提澄清

**当前导航里没有任何 MikroTik 设备**——272 项全部是 http/https（FortiGate 管理页、监控平台、门户）。
唯一与 MikroTik 相关的是 #257 一篇 RouterOS 7.6 中文文档链接。

所以「一些通过本地 winbox 应用打开」意味着需要：
1. 在导航里**能录入 MikroTik 设备**（现在只能录 http/https URL）
2. 卡片上标明**打开方式**，点击时走 Winbox 而不是浏览器

### 3.1 数据模型改动

给 `nav_items` 增加两列（走已有的 `migrate_schema()` 机制，自动 ALTER，不用清库）：

```sql
launch      TEXT NOT NULL DEFAULT 'web'   -- web | winbox | custom
launch_host TEXT NOT NULL DEFAULT ''      -- winbox 用：设备地址（可含端口）
launch_arg  TEXT NOT NULL DEFAULT ''      -- custom 用：自定义协议或附加参数
```

`migrate_schema()` 里加两行即可：

```python
wanted = [
    ("nav_items", "subgroup", "subgroup TEXT NOT NULL DEFAULT ''"),
    ("nav_items", "launch",      "launch TEXT NOT NULL DEFAULT 'web'"),
    ("nav_items", "launch_host", "launch_host TEXT NOT NULL DEFAULT ''"),
]
```

- `launch='web'`（默认）→ 行为完全不变，零回归风险
- `launch='winbox'` → 卡片点击调起 Winbox
- `launch='custom'` → 走 `nh://` 自定义协议（给未来其它本地应用留口）

### 3.2 Winbox 通道

Winbox 是原生应用，**不受浏览器沙箱限制**，而且它支持命令行传参（LibreNMS 等项目就是这么做的）。两条可选路径：

**路径 W1：直接用 Winbox 自己的协议（若有）**
Winbox 4 已有 `winbox://` URI scheme（macOS 上已有第三方实现）。Windows 上是否注册该协议**需要在你机器上实测确认**：

```cmd
:: 在已装 Winbox 的 Windows 上执行，看能否弹出连接窗口
start winbox://198.51.100.13
```

若可用 → 最简单：卡片 `href` 直接写 `winbox://<host>`，零本地组件。

**路径 W2：本地启动器 + `nh://` 协议（确定可行，推荐）**
若 W1 不可用，用自定义协议 `nh://`：

1. Windows 侧放一个启动器脚本，注册 `nh` 协议（注册表）
2. 卡片 `href` = `nh://winbox?host=198.51.100.13`
3. 启动器解析参数 → 调用 `winbox.exe <host>`
4. **账号密码交给 Winbox 自己保存**（Winbox 有地址簿和凭据保存），启动器**不传密码**

> ⚠️ **不要用命令行传密码**。`winbox.exe <ip> <user> <password>` 虽然可行（LibreNMS 就这么做），但**命令行参数在 Windows 进程列表里是明文可见的**——同一个机器上任何用户开个任务管理器/`wmic process get commandline` 就能看到。让 Winbox 自己记住凭据是更安全的做法。

### 3.3 Windows 侧组件（`nh://` 协议注册）

**注册表**（`HKEY_CURRENT_USER\Software\Classes\nh`，不需要管理员权限）：

```
nh                          (默认值) = "URL:notice-hub Protocol"
nh\DefaultIcon              (默认值) = "<路径>\nh-open.exe,1"
nh\shell\open\command       (默认值) = "\"<路径>\nh-open.exe\" \"%1\""
```

**启动器**（`nh-open.exe` 或退而求其次 `.cmd` / PowerShell 脚本）逻辑：

```
1. 解析 %1 → nh://winbox?host=xxx
2. 校验 host 命中白名单（见下方安全项），否则弹窗拒绝
3. 定位 winbox.exe（注册表 / 常见安装路径 / PATH）
4. 启动 winbox.exe <host>
```

**安全要求（重要）**：`nh://` 是**任何网页都能触发的**。恶意页面可以构造一个链接让你点，从而拉起本地程序。所以启动器必须：

- **host 参数白名单校验**（只允许 notice-hub 里的设备地址，或至少限制为 IP/域名格式、拒绝空格与引号以防参数注入）
- 只允许 `winbox` 这一个动作，不做通用「执行任意命令」
- 首次触发时弹确认（可选）

### 3.4 界面呈现

- 卡片上按打开方式显示不同图标/角标：🌐 web / 🟦 winbox
- 卡片 `title` 提示「用 Winbox 打开」
- 新增/编辑表单里加「打开方式」下拉：`网页 / Winbox`，选 Winbox 时显示「设备地址」输入框
- 若本机未注册 `nh://` / 未装 Winbox → 点击时给出友好提示（而非静默失败）

## 4. 账号密码自动填

### 4.1 先说实话：浏览器自带密码管理器已经能做

你选了「A. 用户脚本自动填」。但在写代码之前，有一个**零成本、零风险**的事实需要先摆出来：

> **Chrome / Edge 自带的密码管理器，本来就会对 FortiGate 登录页自动填账号密码，并弹出「要保存密码吗」。**

- notice-hub 的 README 第 120–124 行专门为此做了设计：登录页用**原生表单提交**而非 ajax，就是为了触发浏览器的保存密码提示
- 你去每台 FortiGate 登录一次、点「保存」，之后 Chrome/Edge 每次都会自动填
- 存的是 **Windows 凭据管理器 / 系统钥匙串加密**，不是明文，也不是集中存储
- 272 个站点它会各自记住，不冲突

**这条路满足「自动输入账号密码」，且不需要 notice-hub 存任何密码。**

它的**唯一短板**是首次录入 265 台设备比较费时（每台要登录一次）。而这恰好是用户脚本/凭据库想解决的痛点。

所以真正的问题是：**你愿意为了「批量预置 265 条凭据」的便利，把 265 台防火墙的密码集中到 notice-hub 里吗？**

这个取舍由你定。下面是如果你要做「方案 A」的完整设计。

### 4.2 方案 A：用户脚本 + 服务端加密凭据库

**组成**

1. **凭据库**（后端）：按导航项存 `username` / `password`，加密落库
2. **取用接口**：`GET /api/nav/<id>/credential`，仅授权用户可取，**每次读取写审计日志**
3. **用户脚本**（前端）：Tampermonkey 脚本，托管在 notice-hub（`/tools/nh-autofill.user.js`，Tampermonkey 识别 `.user.js` 会提示安装）
4. **匹配逻辑**：脚本在目标页问 notice-hub「`location.host` 有凭据吗」→ 有则填入并提交

**用户脚本关键实现点**

- 用 `GM_xmlhttpRequest` 请求 notice-hub API —— 它可以**绕过同源策略**，避免跨域 + Cookie `SameSite` 的一堆麻烦
- 脚本用一次性生成的**个人令牌**（存 Tampermonkey 自身存储），不是会话 Cookie
- 按站点写**适配器**：FortiOS 登录页的字段是 `input[name=username]` / `input[name=secretkey]`，填值后需要派发 `input`/`change` 事件并点提交按钮
- 非 FortiGate 的站点（Zabbix / Grafana / 阿里云等）各自适配，或统一降级为「只填不自动提交」

### 4.3 加密设计

**硬约束：Python 标准库没有任何对称加密算法**（`hashlib`/`hmac` 只有哈希与 MAC，没有 AES）。
这个项目目前是「零第三方依赖」的（README + Dockerfile 都强调这点）。所以：

| 选项 | 说明 | 代价 |
|---|---|---|
| 加 `cryptography` 依赖 | AES-256-GCM 标准实现，业界标准选择 | **打破零依赖**，镜像 +约 15MB，需装 alpine wheel |
| 只用标准库自造加密 | — | ❌ **绝对不要**，自己造加密是典型严重错误 |

**若采用，建议设计**：

- 主密钥 `NH_VAULT_KEY`（32 字节）来自**环境变量或独立文件**，**绝不放在数据库里**
- 每条凭据用 `HKDF(主密钥, item_id)` 派生独立子密钥 → 即使数据库泄露、密钥未泄露，也拿不到明文
- 存储格式 `base64(nonce ‖ ciphertext ‖ tag)`，AES-256-GCM，每条随机 96-bit nonce
- 哈希密码（现有的 PBKDF2）与这里的可逆加密是两件不同的事，不能复用

### 4.4 安全前置条件（硬性，未满足前不应上线）

按严重程度排序：

**① TLS —— 这是阻塞项**

notice-hub 现在是 `http://10.0.0.10:8091`，**已实测确认无 TLS**（`https://` 连接失败）。
一旦有了凭据接口，密码会以**明文**在内网传输，同网段任何能抓包的人都能拿到。

→ 必须先上 HTTPS（宿主机上已有 `lucky` 反代和 nginx，可以用来做 TLS 终结）。

**② 登录限流**

上一轮我已经指出：登录失败只有 `sleep(0.4)`，且这个 sleep **占着线程**。凭据库上线后，弱口令爆破的收益从「进导航页」变成「拿到 265 台设备密码」。

→ 必须补按 IP 的失败计数 + 锁定/指数退避。**这是上一轮标为 P2、你选择暂缓的那一项，现在成为前置条件。**

**③ 可见性收紧**

272 项里 265 项是 `member`、3 项 `admin`、4 项 `guest`。
`/api/nav` 是**设计上免登录的公开入口**（`_dispatch` 里 `if path == "/api/nav" and method == "GET"` 在鉴权之前返回）。
→ 凭据接口**必须**独立鉴权、且限定 `admin`（或至少 `member`），绝不能挂在免登录路径上。

**④ 审计**

每次凭据读取都要写 `audit_log`（含谁、何时、哪条设备）。这条已有基础设施，顺手就能做。

> 因为这两个坑都很隐蔽 —— 它们不报错，只是让功能**静默失效**。
> 实测结果见 §6.3。

在排查排版问题时实测出来的，**与第 1 期改造强相关** —— 卡片左上角那个在线/离线状态点，
对 265 台 FortiGate 来说目前**永远是灰色「未探测」**，作为「快速找到可用系统」的线索完全没用。

### 6.1 `is_private_host()` 漏判 `198.18.0.0/15`（含 `198.19.x.x`）

`is_private_host()` 是手写的，只匹配 `10.` / `192.168.` / `127.` / `172.16-31.`：

```python
return bool(
    ip.startswith("10.") or ip.startswith("192.168.") or ip.startswith("127.")
    or re.match(r"^172\.(1[6-9]|2\d|3[01])\.", ip)
)
```

但你要管理的 265 台 FortiGate 全在 `198.19.x.x`，而 **`198.18.0.0/15` 是 RFC 2544 保留段**，
Python 标准库明确认定它是内网地址 —— 手写的这段判断漏了它：

```
198.51.100.13   ipaddress.is_private=True   is_global=False   ← 标准库：是内网
                 is_private_host()=False                       ← notice-hub：当成公网
```

**实测后果**（这台设备 TCP 实际上是通的）：

```
probe_url('https://198.51.100.13:9443')
  -> {'ok': None, 'reason': '非内网地址，已跳过探测'}    ← 永远"未探测"
probe_url('https://10.0.0.10:3000')
  -> {'ok': True, 'ms': 0}                              ← 正常
```

因为 `NAV_PROBE_ALLOW_PUBLIC = False`，`probe_url` 会直接跳过所有它认为「非内网」的地址。
**所以即使你把那 265 项的 `probe` 开关打开，它们照样全显示「未探测」。**

**修复**：改用标准库判断，一行即可，且更正确（能覆盖 CGNAT `100.64/10`、`169.254/16` 等）：

```python
import ipaddress
def is_private_host(host: str) -> bool:
    try:
        ip = ipaddress.ip_address(socket.gethostbyname(host))
    except (OSError, ValueError):
        return False
    return ip.is_private or ip.is_loopback or ip.is_link_local
```

### 6.2 探测是串行的，撑不起 265 个目标

`nav_probe_loop()` 逐个串行探测，每个超时 2.5s：

```
265 台 × 最坏 2.5s = 11.0 分钟/轮
而探测间隔 NAV_PROBE_INTERVAL 只有 60 秒     ← 串行根本跑不完
```

这大概就是当初把 265 项 `probe` 全关成 0 的原因（目前 `probe=1` 只有 7 项）。

**修复**：用 `ThreadPoolExecutor`（如 32 并发）改造 `run_nav_probe()`，
265 台 × 2.5s / 32 并发 ≈ **21 秒/轮**，60 秒间隔完全够用。

> 这两个是「排版改造」的配套项：分组折叠和 Ctrl+K 解决「知道要找什么」，
> 而**状态点解决「打开哪个是通的」** —— 状态点不修，265 项就都是一片灰。

## 8. 已落地的 Winbox 本地联动（及一个必须记住的坑）

### 8.1 为什么需要本机装一次

Winbox **默认不注册任何 URL 协议**，浏览器无法直接唤起它。所以采用「本机协议处理程序」方案：

| 文件 | 作用 |
| --- | --- |
| `nh-setup.cmd` | 薄包装，双击即可；纯 ASCII + CRLF |
| `nh-setup.ps1` | 自动探测 / 文件选择框指定 `winbox.exe`，写 `HKCU\Software\Classes\nh` |
| `nh-open.ps1` | 协议处理程序本体，校验地址后 `Start-Process` 拉起 Winbox |

只写 `HKCU` 和 `%LOCALAPPDATA%\notice-hub\`，**不需要管理员权限**。
三个文件必须放在同一个文件夹里，缺 `nh-open.ps1` 会明确报错。

### 8.2 坑：浏览器会把 `nh://winbox?host=X` 规范化成 `nh://winbox/?host=X`

这是本项目最隐蔽的一个 bug，值得单独记一笔。

**现象**：装完安装器自测通过（Winbox 起来了），但从网页点卡片却弹「无法识别的链接」。

**原因**：自定义协议里 `winbox` 被浏览器当成**主机名**，序列化时会补出一个空路径。
于是真正交给处理程序的字符串是：

```
nh://winbox?host=10.0.0.9      ← 我们写在 href 里的
nh://winbox/?host=10.0.0.9     ← 浏览器实际发出去的（winbox 后多一个斜杠）
```

**为什么自测没发现**：安装器自测是直接 `powershell -File $Handler 'nh://winbox?host=...'`，
把字面量原样传进去，**绕过了浏览器**，所以永远测不出这个问题。

**修复**（两处，缺一不可）：

1. `nh-open.ps1` 的首个正则改为 `^nh://winbox/?\?(.+)$` —— `/?` 让斜杠可选；
   同时保留路径形式 `nh://winbox/<host>`、旧协议 `winbox://<host>` 作为兼容。
2. `nh-setup.ps1` 自测改为**两种形式都测**，其中带空路径的那条是浏览器真实发出的形式。

**回归测试**：`tests_api.py` 把 `.ps1` 里的正则抽出来喂真实链接（含规范化形式、
恶意链接）；`tools/test_frontend.js` 断言自测覆盖了带空路径的形式。
两条都做过 A/B：把正则改回旧写法，测试精确失败。

### 8.3 处理程序怎么更新（已做成自动拉取）

处理程序是**拷贝**到 `%LOCALAPPDATA%\notice-hub\` 的，不会自动跟随服务端更新 ——
本轮就真的踩了这个坑：服务端已经修好，同事机器上还是旧的一份。

现在 `nh-setup.ps1` 会**优先从门户拉最新处理程序**，三级回退保证安装永远能走完：

1. 门户 `http://10.0.0.10:8091/tools/nh-open.ps1`
2. 同目录下的 `nh-open.ps1`（断网 / 门户没开时）
3. 本机已装的那份（至少不让安装失败）

拉回来的内容要过校验才会装，**旧版会被明确拒收**：必须含 `param(`、`[regex]::Match`、
`$NhHandlerVersion`、`nh://winbox/?`、`Start-Process`，且不含 `Invoke-Expression`。

于是以后要更新处理程序，同事只需要：

```
重新双击 nh-setup.cmd        （连 nh-open.ps1 都不用手工下载了）
```

安装时会打印来源和版本，并告诉你是不是刚更新过：

```
处理程序 ：C:\Users\xxx\AppData\Local\notice-hub\nh-open.ps1
来源     ：门户 http://10.0.0.10:8091/tools/nh-open.ps1
版本     ：nh-open 2026-09-29
（已从 nh-open 2026-09-20 更新到 nh-open 2026-09-29）
```

想查本机装的是哪一版、有没有装旧版：

```
nh-setup.cmd -Show
```

装的是旧版时它会直接红字告警「这一版可能不认浏览器发来的链接」。

其他参数：

| 参数 | 用途 |
| --- | --- |
| `-Offline` | 不联网，只用同目录的 `nh-open.ps1` |
| `-BaseUrl http://HOST:PORT` | 从别的门户地址拉取 |

> 改动 `nh-open.ps1` 时**记得同步改里面的 `$NhHandlerVersion`** —— 安装器靠它判断新旧。
